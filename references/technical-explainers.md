# 面向非算法读者的 AI 技术长文

这份文件用于模型技术报告、论文领读、技术播客整理，以及面向产品经理和普通 AI 读者的架构科普。目标是让读者真正建立结构认识，同时保留会影响判断的技术精度。

## 先找到整篇文章的解释主线

不要按照技术报告的目录逐项翻译。先寻找一个能够解释多数创新为何出现的核心问题，再让章节围绕它推进。

例如，一份报告同时扩展上下文、网络层数和专家数量时，可以追问：增加的物理容量怎样变成模型真正能够调用的有效容量？随后分别解释每个方向遇到的退化、拥堵或训练问题，以及对应机制怎样解决它。这样的框架必须来自材料本身，不能为了对称强行凑轴。

一旦用户确认了“长、深、宽”之类的中文坐标，正文、章节标题、图注和封面统一使用同一组词。不要在“高、深”“宽度、专家容量”等近义说法之间来回切换，让读者不断重新定位。

## 先唤醒最小结构，再进入创新

非算法读者通常不是完全没听过 Transformer，而是忘了各模块的位置。正式解释创新以前，用一小节和一张简单图恢复最小结构：

- Token 序列会经过每一个 Block。
- Attention 负责不同 Token 之间交换上下文。
- FFN 或 MoE 负责逐个加工已经获得上下文的 Token 表示。
- 多个 Block 依次堆叠形成网络深度。

这张地图只负责给后续术语定位。不要在开头顺手讲完 Transformer 历史、全部公式和实现细节。后面出现一个机制时，先告诉读者它位于哪一层、处理哪条信息流，再解释它怎样工作。

## 每个机制只回答一条完整因果链

写作时在内部完成这条链：物理扩展带来什么问题，旧方法为什么不够，新机制改变了哪个动作，最终让哪部分容量真正可用。正文可以自然展开，不必把它做成每节重复出现的固定模板。

第一次出现术语时，优先按下面顺序解释：

1. 用一句白话说明它在系统里负责什么。
2. 用一个足够简单的比喻建立画面。
3. 立刻回到真实结构，说明输入、处理动作和结果。
4. 只有公式或底层细节会改变理解时才继续下钻。

一个比喻只承担一个任务。比喻需要新增太多角色、规则和例外时，它已经比原机制更难懂，应当删掉或换成直接描述。

## 相近术语按阅读需要区分

技术资料经常同时出现基础结构、改进版本和组合名称。正文实际讨论 Gated MLA 时，先把 Gated MLA 作为一个完整模块讲清楚：它做什么、解决什么问题。只有读者必须理解 MLA 与 Gated MLA 的差别，或用户明确追问时，才拆开解释基础结构与新增门控。

同一个组件不要先以组合名出现，随后又把其中一部分当成并列模块重复介绍。术语区别如果不会改变后文判断，就留在注释或研究底稿，不占正文注意力。

## 发布稿只保留结论，不保留纠错现场

研究和协作过程中可能需要修正 NotebookLM、媒体解读或早期草稿。修改后的正文直接采用已核实的说法，不写“这里需要校准前面的材料”“更准确地说”之类编辑痕迹，也不向读者交代作者如何改稿。

解释一个数字或机制时，先写它可以怎样理解。只有一种误解非常常见且会影响结论时，才补一次必要对照。不要连续写“它不意味着……也不能理解为……”，让真正含义迟迟不出现。

## 精确配图服务于理解

技术长文的图片分为三类：官方结构图或数据图负责证据，重新绘制的流程图负责解释，封面负责建立主题。三者不能互相替代。

需要准确中文、数字、箭头和模块关系的流程图，使用 SVG、Canvas、Pillow 或其他可控方式绘制，不交给生成式图片模型猜文字和拓扑。一张图只解释一个主要关系，颜色、字体、圆角和线宽在全文保持一致。

交付前按原始尺寸检查每张自绘图：

- 外框与内部卡片之间留有明确边距，内部边框不能与外框重合。
- 箭头从边框中心出发并准确落到目标边框，不穿过文字。
- 标题、标签和图注没有截断、挤压或意外换行。
- 同层元素对齐，连接线粗细和圆角一致。
- 概念图在图注中标明“概念配图”，官方图保留准确来源。

微信公众号封面与正文图片分开交付。封面使用约 2.35:1 的横版比例，必须带缩略图状态下仍能读清的主题文字；正文 Word 不默认嵌入封面。

## 长稿协作与最终交付

一万字以上的技术长文继续按章节确认。用户调整一个术语、比喻或章节时，先只修改对应范围；得到确认后再进入草稿和下一章，避免一次改动牵连已经成立的内容。

合稿时重点删除重复定义。同一术语只在首次出现处完整解释，后文直接使用。Word 投稿稿保持适合平台复制的简洁排版，图片连续编号并紧跟对应论点。交付时同时说明正文汉字数、图片数量和文件页数；字数以正文汉字为主，页数只作为排版参考。
